## Mechanism 1: trusted reservation and initialized-prefix bulk copy

Read complete `Vec::extend_trusted` (3761–3790), `extend_desugared` (3733–3755), `append_elements` (2730–2736), the selected public reserve/pointer/length wrappers, all 63 lines of `spec_extend.rs` and all 33 lines of `set_len_on_drop.rs`. Relevant `RawVecInner` bodies include `reserve` (545–565), `current_memory` (526–540), `needs_to_grow` (626–628), `grow_amortized` (639–669), `grow_exact` (671–692), pointer/capacity publication (631–637), `finish_grow` (766–788), error handling/layout helpers (790–822), and the element-size minimum (158–170). The JSON supplies additional exact wrapper/invariant spans. These are selected portions of larger files, not a complete Vec/RawVec review. [Pinned Vec implementation](https://raw.githubusercontent.com/rust-lang/rust/1159e78c4747b02ef996e55082b704c09b970588/library/alloc/src/vec/mod.rs), [pinned RawVec implementation](https://raw.githubusercontent.com/rust-lang/rust/1159e78c4747b02ef996e55082b704c09b970588/library/alloc/src/raw_vec/mod.rs).

The trusted path reserves from the exact upper bound before obtaining a write pointer. Rust's unsafe `TrustedLen` contract permits exactly that many elements or divergence; ordinary equal-looking size hints are not a substitute. A `None` upper bound denotes an actual length beyond `usize::MAX`, so the path rejects it rather than consuming the iterator. The general iterator path can run user code and publishes initialized length after each item. `SetLenOnDrop` instead maintains a local count and writes it back on scope exit, including unwinding. Its stated purpose is avoiding alias-analysis interference between data writes and header-length updates. `append_elements` reserves, copies a nonoverlapping initialized range and then increments length. The consuming `IntoIter` specialization forgets the transferred elements; the slice specialization requires `T: Copy`. These ownership premises differ materially from Minyar reference Lists.

`grow_amortized` checks required element count, computes a geometric target with a minimum, validates the array layout, performs allocation/growth and publishes pointer/capacity only after success. The inspected `Layout::repeat` chain checks multiplication and aligned `isize` limits. `Allocator::grow`'s contract and default body (core allocation 166–229) preserve the old allocation on returned error and invalidate the old pointer on success. That fallible API cannot establish equivalent Minyar fatal-error state or finite-pool admission.

**Minyar mapping.** `minyar_list_appended` (collections 201–225) already reserves trusted known size and retains geometric growth while any retirement task remains after common header allocation. Its scalar prefix currently calls `minyar_list_add` once per source element. On the valid scalar path, add (104–127) performs a store/length increment without retain, release or poll; capacity has already been prepared for `n+1`. A fresh destination cannot overlap its protected source. This makes Rust's initialized-prefix copy pattern a plausible small internal refinement, without importing Rust iteration, borrowing or panic semantics.

**H1, new proposal; not accepted:** when the compiler-provided element kind is scalar (`references == 0`), copy exactly `n * sizeof(long long)` initialized prefix bytes, publish result length `n`, then execute the existing tail add/take call. Skip the copy for `n == 0` because the source buffer may be NULL. Keep the reference path unchanged, including immortal/null references. Do not infer scalar status from current reference counts or contents.

The conditional source argument begins *after identical reservation*: source/destination headers and allocations are valid, the source has `n` initialized slots, the destination has capacity at least `n+1`, and the supported ABI has eight-byte slots. Reservation's existing size checks establish representable copy size. Each old scalar store has no ownership/service effect and no callback. Under the single-mutator, non-reentrant contract, intermediate destination lengths are unobserved. A bulk copy establishes the same initialized prefix; publishing `n` leaves the same spare capacity; the unchanged tail store cannot grow. Allocation addresses, request order, pending tasks, scheduler/cache state and all cleanup hooks therefore stay unchanged within this phase, even with debt. This is a conditional argument about a proposed rewrite, not a verified implementation proof. Invalid fabricated native headers are outside it.

**Expected benefit and cost:** remove the source-level per-element add path and repeated length publication; retain linear copying and exactly the same allocation footprint. Generated machine code may already optimize the loop, and a library copy may cost more for tiny Lists, so neither reduced CPU nor fewer machine instructions is established. Complexity is one scalar/reference branch, one guarded copy and one length assignment; no extra metadata. Reject if validation requires moving cleanup hooks, relaxing checks, adding `restrict` promises or changing capacity.

**Independent red-first falsification proposal, all pending:** derive expected values and capacity from a separate mathematical sequence; inspect every prefix element and tail for lengths 0,1,2,3,7,15,31,1024 and boundary-adjacent lengths. Include negative/minimum/maximum Integer bit patterns, Boolean/Character slots, an unchanged retained source alias, and both tail transfer flags. Use a copy/store-work observer to distinguish the proposed bulk path from a correct scalar-loop mutant; that oracle demonstrates path/work selection only. Require identical ordered managed requests, resize requests, helper events and every public poll return, exact post-drain ownership/bytes and a follow-on pool allocation trace. Preserve object/frame/chunk debt after common header service at K1/K32, including cases where intermediate growth is necessary for admission. Reference controls must retain mortal/null/immortal members and an aliased tail with exact retain/transfer counts. Error controls require the same overflow diagnostic and header/backing failure order, not recoverable-error equivalence. Future owner-authorized native/sanitized and generated O0/O2 checks are needed; none ran here. Small-input and already-optimized-loop controls can falsify the proposed practical benefit.

**Capacity rejection:** Rust starts at 8 byte-sized elements, 4 moderate-sized elements or 1 large element. Minyar's pooled List starts at 3 eight-byte slots: 8 header bytes + 24 payload bytes fit a 32-byte block. Porting Rust's 4-slot minimum would request 40 bytes and charge 64. Minyar's other profiles start at 2 and have a separate arena transition policy. Rust also has zero-sized types unavailable in this List ABI. Copying these constants, exact-reserve semantics or unchecked optimizer assumptions is not justified.

## Mechanism 2: alias-safe append through growth

Read complete libc++ `basic_string::append(pointer,count)` (3016–3032), `__grow_by_and_replace` (2692–2726), `__grow_by` (2731–2762), `__grow_by_without_replace` (2764–2779), `max_size`/capacity (1284–1304), `__recommend`/alignment (2284–2302), representation/accessors and annotation helpers (793–915, 2090–2110, 2164–2302). Read both allocation-at-least branches, allocator-trait dispatch/max-size bodies, `char_traits<char>::copy`/assignment, the complete relevant `__constexpr_memmove` body and scope-guard implementation. Large unrelated constructors, inserts, iterators, alternate character traits and system allocator implementations remain unread. [Pinned libc++ string implementation](https://raw.githubusercontent.com/llvm/llvm-project/b708aea0bc7127adf4ec643660699c8bcdde1273/libcxx/include/string).

A sufficient-capacity append copies into the suffix and then publishes size/terminator. For a source subrange contained in the old character prefix, the ranges are disjoint. The growth path allocates distinct replacement storage, copies the old prefix and appended source while old storage remains valid, then deallocates old heap storage and publishes the new representation. `char_traits::copy` explicitly requires nonoverlap even though its current leaf uses a memmove helper; that implementation detail does not grant arbitrary overlapping-copy semantics. Allocation uses `__allocate_at_least`; the returned count, rather than merely the recommendation, becomes stored capacity. The inspected guard restores sanitizer annotations on scope exit; it is not a Minyar cleanup service.

The subtraction-based spare-capacity test and growth delta reject size beyond `max_size` before allocating. On the growth branch, the unsigned delta is mathematically `n - (capacity-size)`, since `n` exceeds spare capacity; its check against `max_size-capacity` precedes geometric recommendation. Recommendation counts the terminator and respects representation/alignment constraints. These are C++ code-unit/capacity rules, not UTF-8 scalar validation or a Minyar failure-policy template.

**Minyar mapping and disposition:** consuming Text join (runtime 484–524) already gates mutation on exact unique owning kind and no backing root, grows geometrically, rebases self-RHS bytes after realloc, copies before updating metadata and invalidates Unicode offsets. Borrowed join copies. A live sliced view retains the owning root (817–838), so it prevents unique-root reuse; a left view cannot be mutated because `backing` is non-NULL. Deferred owners can conservatively prevent reuse. This is already present, not a new port.

A libc++ allocate-copy-free growth replacement would change Minyar's resize requests and simultaneous live storage. System realloc, same-base buddy growth and replacement allocation have different admission effects. A smaller recommendation or allocator-returned slack can suppress a later service hook. The recorded Bytes late-debt counterexample applies even when debt was absent at the earlier capacity choice. Neither allocator slack nor pre-service uniqueness probing is recommended; both would require policy/history complexity unsupported by this comparison.

**Independent falsification proposal, all pending:** forced-moving versus same-base growth, sufficient spare capacity, self-RHS and genuine aliases/views; check exact bytes and root ownership before/after. Use known ASCII and indexed `Aé🙂Z`, then query characters and nested slices after append to detect stale indexes. Require identical service/request traces and header/data recovery. A stale-self-pointer mutant must fail the moving case; omitting root retain must fail the surviving-view case. These are implementation controls, not new tests or ports in this report. No benefit hypothesis is added because Minyar already has the relevant mechanism.

## Mechanism 3: conservative cached ASCII knowledge

Read complete Swift `CountAndFlags.init(count:isASCII:isNFC:isNativelyStored:isTailAllocated:)` (792–826), specialized constructors (843–869), masks/accessors and invariant checks (761–931), raw initialization (305–325), small-count/ASCII queries (639–665), representation dispatch (283–302, 474–505, 1132–1158) and `_StringGuts` ASCII/fast-storage queries and invariant bodies (95–142, 154–218). Remaining bridge/native-storage and String APIs were not reviewed, and neither unavailable guessed append file is counted. [Pinned Swift StringObject](https://raw.githubusercontent.com/swiftlang/swift/1ff1cc1170617ab23ab74aa8b741c8daca1903f6/stdlib/public/core/StringObject.swift), [pinned StringGuts](https://raw.githubusercontent.com/swiftlang/swift/1ff1cc1170617ab23ab74aa8b741c8daca1903f6/stdlib/public/core/StringGuts.swift).

The useful mechanism is an explicit certificate separate from code-unit count and storage mode. The ASCII flag denotes known ASCII and entails NFC; native storage entails tail allocation. Constructors record these implications and internal checks assert them; these checks do not independently scan bytes or make an arbitrary caller's flag truthful. `_StringGuts.isFastASCII` additionally requires fast UTF-8 storage. Clear/unknown flags therefore cannot be replaced by a positive certificate merely because contents happen to look ASCII. Swift's count is code units, and these files do not establish Swift Character/grapheme semantics suitable for Minyar.

**Minyar mapping:** the existing encoding already represents the needed certificate: known `character_length == byte_length` proves ASCII for truthful valid Text. Conversely, known length with NULL offsets is consumed as ASCII by character lookup and slicing. Borrowed and consuming joins preserve the certificate, while aggregate join at the frozen baseline still returns unknown. Unknown/malformed operands must continue through lazy validation. Unicode count alone cannot be propagated into a NULL-index Text; the rejected `é🙂` view would return UTF-8 byte 195 instead of scalar 233 and permit a split encoding.

**H2, existing isolated proposal, no new credit:** conjunct every fragment's existing ASCII certificate during aggregate join's current sizing pass; choose the total byte length as result count only if all qualify. This is the already reviewed aggregate patch, not a new Swift port. Concatenation preserves the ASCII property by direct byte reasoning, including embedded NUL; this conjunction is our compatibility inference, not a claim that the unavailable Swift append sources were read. Empty input permits the vacuous certificate. No additional flag, packed header, normalization, grapheme logic or root-index ownership change is needed.

The expected work benefit is avoidance of one later certified-ASCII index scan. Cost is certificate work during sizing, including unknown/no-query inputs that obtain no scan saving. Existing reports retain this tradeoff and an approval conditional on final gates; this lane adds no timings or acceptance evidence. Independent proposal controls are known/unknown ASCII, unknown empty operands, zero/single/many fragments, embedded NUL, a certified ASCII view sliced from indexed Unicode, genuinely Unicode fragments, malformed unknown input, immortal cached values, aliased sources and byte-length-only use. A forced-known Unicode mutant must fail character/nested-slice checks; an always-unknown mutant must fail the scan-work oracle while remaining semantically correct. Preserve overflow precedence, byte copy order, allocation requests and all helper/direct-poll events under object/frame/chunk debt. Existing evidence must remain source-matched; no checks were rerun here.
