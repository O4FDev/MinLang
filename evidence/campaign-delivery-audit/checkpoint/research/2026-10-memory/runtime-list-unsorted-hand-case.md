# Adapted three-move allocator case

The separately authorized adapted length-15 case passed four isolated builds and four executions: original versus guarded reservation, native O2 and C ASan+UBSan O1. This is an actual-runtime adaptation of the independent audit's unsorted-list argument, **not execution of its literal hand layout**. No production source, pending-task policy or public call boundary changed.

[Pre-replay derivation](runtime-list-unsorted-derivation.md), [amended preregistration](runtime-list-unsorted-hand-case-preregister.json), [final durable results](evidence/runtime-list-unsorted-hand-case/run-6vtv17ib/results.json) and [archive inventory](evidence/runtime-list-unsorted-hand-case/run-6vtv17ib/archive-index.json) preserve the rules, expectations, commands, copied runtime/helper/fixture sources, observer patches and complete outputs. LeakSanitizer is disabled. There is no generated-language or timing claim, and installed Darwin Clang/sanitizer prerequisites remain external.

Actual allocation/free APIs construct a complete canonical 4096-byte partition, initialize every live raw blocker byte, then free the declared blocks. The real common header selects address 864. At the post-header boundary the ordered free lists are `[800]`, `[64,128,896]`, `[256,640]`, `[2560,2048]`, `[1024]`, `[3072]` for 32 through 1024 bytes. Their mask is 63 and current charge is 1568. Matched test-only scheduler residues recent-turn 1/next-queue 2 are set before the public append; no tasks, post-header callback or allocator-state injection are used. This residue setup is explicitly outside a claimed all-public-API history.

Original backing moves 800 to 64 to 256 to 2560. Alignment prevents the first two in-place growths; the occupied buddy at 384 prevents the third. It restores 64 before the surviving `[128,896]` tail and 256 before 640. Direct reservation selects the same final 256-byte block at 2560. Complete ordered previous/next links and all 128 map bytes match the derived expectations and each other. Initialized headers, source/result slots and all nine raw blockers match; final List length/capacity are 16/31 with values 0 through 14 followed by 919. All scheduler roots, cursor/turn/cache fields, object/requested accounting and current allocator charge also match.

Final current charge is 1824 bytes and RC requested bytes are 448; raw blockers are counted independently in pool charge. Both high-water values remain 4096 because setup first fills the pool. Successful allocation counts at append completion are 28 versus 25 and allocator step telemetry differs. These metrics are deliberately excluded from the decision-state relation; the states are not literally identical.

Both versions then receive raw requests 32,64,128,4096, compare success/normalized addresses and full decision snapshots, free probes in reverse order, release the Lists, drain reclamation and free blockers. They recover exactly zero objects, requested bytes and pool charge. Newly allocated raw payload and spare List capacity are not read; no resize copying uninitialized storage occurs. Telemetry, padding/free/spare bytes, sanitizer internals and OS/timing observations remain outside this comparison.

Two calibration failures remain visible. [run-wi4i4x51](evidence/runtime-list-unsorted-hand-case/run-wi4i4x51/results.json) completed all executions but rejected an off-by-one expected setup-allocation count: the source header plus 22 partition pieces make 23 setup allocations. [run-lun_lnzg](evidence/runtime-list-unsorted-hand-case/run-lun_lnzg/results.json) rejected the literal post-header list oracle: available 32-byte free nodes make the actual header select 864, before a 64-byte block could be selected. Neither is a runtime defect. Parent authorized this genuine prefix without injecting a callback, and the documented allocator-rule derivation supplied the adapted expectations before the final labeled replay.
