PNG input/domain and arithmetic findings:

- `saveScreenshot` publicly accepts a path, not dimensions. `openWindow` accepts signed64 Minyar integers and rejects dimensions outside1–16384 before narrowing to C `int`. Actual screenshot dimensions subsequently come from GLFW `int` framebuffer queries at window creation and every `nextFrame`; no application framebuffer cap or GLFW size-limit call is installed. GLFW distinguishes pixel framebuffer sizes from screen-coordinate window sizes and permits independent framebuffer changes. Therefore the initial16384 window validation is not a proof of a permanent16384 framebuffer bound. Negative mocks test defensive behavior only; they do not claim ordinary GLFW returns negative sizes. [GLFW framebuffer query](https://www.glfw.org/docs/latest/group__window.html#ga0e2637a4161afb283f5300c7f94785c9), [GLFW framebuffer guide](https://www.glfw.org/docs/latest/window_guide.html#window_fbsize).
- PNG dimensions must be positive and at most2^31−1; a chunk data field is also limited to2^31−1 bytes. Multiple consecutive IDAT chunks are legal. The present writer emits exactly one IDAT. [PNG3 chunk layout](https://www.w3.org/TR/2025/REC-png-3-20250624/#5Chunk-layout), [IHDR dimensions](https://www.w3.org/TR/2025/REC-png-3-20250624/#11IHDR), [IDAT rules](https://www.w3.org/TR/2025/REC-png-3-20250624/#11IDAT).
- For positive width `w` and height `h`, independent exact arithmetic is `P=4*w*h`, `R=(3*w+1)*h`, allocated compressed capacity `A=R+5*(floor(R/65535)+1)+6`, and actual encoded length `L=R+5*ceil(R/65535)+6`. The zlib prefix/checksum contribute6 bytes; each nonempty stored block contributes5 bytes. At an exact raw multiple of65535, allocation capacity has five unused bytes, which are not emitted. This slack is not a correctness defect.
- Supported native targets use64-bit `size_t`; the fixture asserts that and32-bit `int`. At `w=h=INT_MAX`, `P=18446744056529682436`, `R=13835058044544745474`, and `A=13836113591812964355`, all below `SIZE_MAX=18446744073709551615`. Monotonicity proves every positive32-bit dimension pair fits these `size_t` products/additions. This is representability, not successful allocation or a legal object on a particular allocator. Endpoint sizes exceed signed pointer-difference range and actual address-space/resources. A32-bit size_t wrap scenario is outside the supported ABI; dimensions aboveINT_MAX cannot enter these framebuffer fields. No overflow defect was invented by narrowing the seam.
- Row/source expressions cast before width/height multiplication. `height-1-y` stays nonnegative/in-range and loop increments stop atINT_MAX without overflowing. In contrast, `x*4` and `x*3` are signed32-bit operations before pointer addition. The first RGBA overflow is `x=536870912` (width536870913), while RGB first overflows at `x=715827883` (width715827884). Width536870913/height1 still has legal single-IDAT length1610735631, so a chunk-limit guard alone does not eliminate the RGBA issue. This is a source-grounded conditional defect; the loop at those widths was not executed. C11 draft N1570 sections6.3.1.8 and6.5 paragraph5 establish the conversion/result-range rules. [WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf).
- Positive dimensions already fit PNG dimension fields and `GLsizei` on this ABI. GL_RGBA/GL_UNSIGNED_BYTE row bytes are4*w, consistent with default alignment4; actual pixel-pack state, readback errors and driver framebuffer limits remain outside this fixture. OpenGL reports an error for negative readback sizes; it does not provide an application-side promise of successful huge readback. [Khronos ReadPixels reference](https://raw.githubusercontent.com/KhronosGroup/OpenGL-Refpages/main/gl4/glReadPixels.xml).
