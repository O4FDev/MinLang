## Measurements, setup and observability

| Study | Timed boundary | Material work/state |
| --- | --- | --- |
| Aggregate Text | C clock constructor to reporting destructor | Argument parsing, file reads, immutable fragment assembly, repeated aggregate joins, ownership hooks, checksum and final output. Fragment construction is before the loop but **inside the clocks**. No separate final drain. |
| Borrowed-copy ASCII Text | C clock constructor to reporting destructor | Builds the source first, optionally certifies it, then repeats borrowed joins and queries, compiler ownership/frame work and three prints. Source setup remains timed. |
| Scalar List | Clocks around the C repetition loop | Source construction, fixed-pool constructor, final source release and output are excluded. Fresh result construction, copying, checksum loads, release and its service are included. No separate measured final drain. |

Text clock boundaries omit loader work before the constructor and OS teardown after the destructor. Printing occurs inside the program; final libc flushing after the observer's last clock is not guaranteed to be included. Aggregate `cpu_ns` is `CLOCK_PROCESS_CPUTIME_ID`, while user/system fields are separate `getrusage` snapshots taken at slightly different endpoints. It is inaccurate to label the primary value precisely as the sum of those saved user/system fields, or as pure loop CPU. Wall/CPU clocks likewise differ by small endpoint overhead. The observed occasional sub-microsecond CPU/wall inversions do not invalidate the measurements.

Each timed invocation is a fresh process: heap/free-list and runtime metadata start anew. One whole-program warmup per variant/mode warms external caches but does not share the allocator or live Text index with the next process. Within a batch, inputs are reused, allocations/reclamation repeat, libc reuse and caches can settle, and each newly allocated result is queried cold. These are repeated hot-input workloads with fresh result metadata, not first-touch application latency. No cache flush, CPU pinning/frequency control, malloc perturbation or randomized allocator history is present. Fixed List uses one deterministic source-preparation history in a prefaulted 8 MiB pool. Aggregate outputs have mostly five fragments (unknown has a sixth); fragmentation/cardinality tradeoffs beyond these shapes were not measured.

The aggregate LLVM loop calls `minyar_join_texts`, installs the returned owner, chooses `byteLength` or `length`, accumulates the result and calls `minyar_rc_step`. Runtime declarations do not claim purity/readnone, and these links have no LTO. Frozen machine code retains that loop: candidate calls at `0x100000918` (join), `0x100000928` (owner), `0x100000940/94c` (byte/character query), `0x100000958` (step), and the backward branch at `0x100000960`. Candidate sizing code actually loads the certificate and combines it (`0x1000028a4` onward), retains copy/allocation code, and stores the selected count. This is no dead aggregate benchmark.

Scalar List disassembly retains calls to `minyar_list_appended` and a full source-element load / `minyar_list_add` loop in both variants. System guarded copy loop is `0x100001770–178c`; fixed binaries also retain the public append path and copy loop. The C fixture's weaker first/last-element checksum did **not** allow the compiler to delete the middle-copy work in these frozen binaries. Ordinary growth likewise retains the fill loop. These observations constrain optimizer-artifact explanations; they do not prove identical instruction layout or allocator/cache cost. The 1.6% fixed growth difference cannot be causally assigned from equivalent source behavior alone.

Aggregate baseline batch means are 182.092 ms known, 70.907 ms short, 177.723 ms unknown, 192.960 ms Unicode and 122.508 ms no-query. Short/no-query hit the one-million-loop cap and miss the intended 150–300 ms target; all rows remain. ASCII baseline batches span approximately 8.4–28.2 ms with recorded 1,000 ns CPU resolution. List baseline batches span approximately 20–67 ms. Clock quantization is small relative to those totals; setup, code layout and uncontrolled host effects still matter for sub-percent differences. Aggregate maximum paired wall/CPU is approximately 1.0152; no large measured scheduling stall is evident in those rows, but that does not establish host isolation.

## Output oracles and count causality

The audit connects every paired duration back to the original journal stdout/stderr and argv. Text block labels are unique; blocks 0–11 occur once per mode. List pair order is reconstructed from the execution journal and case arguments. Return codes, checksums and exact saved clock dictionaries agree. All calibration and warmup records are present; they are excluded from estimators by design, not discarded adverse observations. The timing stdout expectations are independently calculated rather than comparing two implementations or trusting a hash.

Aggregate expected output comes from Python decoding literal `\\n`/`\\t` in the pinned input strings, appending independently specified `tail` for the unknown mode, and calculating Python Unicode scalar/UTF-8 lengths. It checks every **final** result byte, accumulated scalar/byte lengths and the final alias-equality line. These fixed inputs exercise only those escapes. It does not check every intermediate result's bytes, nor prove alias identity/immutability under mutation: `alias == source` is value equality and both aliases could in principle change together. The separate semantic count fixture checks saved raw source and a consuming append; this is the stronger alias control and is not silently attributed to the timing loop.

ASCII timing expects independently specified initial/scalar/byte totals. It does **not** print joined bytes or check every character; its semantic count fixture supplies those separate checks. List timing independently computes the arithmetic-series tail checksum or `(length-1)*37*iterations`; its first/last-only oracle cannot detect arbitrary middle-element corruption. The separate List correctness fixture checks every scalar, the source alias, references/transfer, capacities and recovery. Passing timing stdout is therefore evidence of the particular observed values, not a complete semantic proof.

The ASCII first-count record independently shows known long input scanner bytes 8,454,272→65,536 and builds 129→1 for 128 joins; unknown 128→128, no-query 1→1 and Unicode 129→129. This is **scanner work**, not CPU instructions or byte loads. Both copied-join variants retain two allocation/service opportunities, and isolated pending debt retains 64 units. The timing binary has no inserted counters; counted and timing fixtures have different repetition counts.

For the refined aggregate pair, **98 phase event arrays** match in requests, copy, helper and all-poll fields, with only index-count differences. I independently summed kind-5 poll events to verify call counts, offered budgets and returned work, without adding nested helper work twice. Ordinary known-ASCII construction has 17 polls / 544 offered / two units, despite nine idle helper calls. Native object/frame/chunk join controls preserve two allocation services and 64 units. Successful final recovery records match; arena recovery is explicitly inapplicable and malformed trap rows do not claim recovery. This repairs the old observer's coverage gap. None of that instrumentation appears in the timing runtime; the corrected count records do not retroactively change the timing binaries.

Under truthful typed Text metadata, the exact candidate avoids the known ASCII result scan and adds certificate reads in its existing sizing pass, without changing allocation/copy/service order. This is the causal code/count argument. Paired CPU measurements then associate the exact compiled change with a batch cost reduction. They do not uniquely allocate that reduction to instruction counts, exclude all code-layout/cache/frequency mechanisms, or prove a global scheduler/admission theorem. List's fewer idle allocation opportunities likewise are not fewer measured reclamation units. The separate admission reviews' mathematical premises and excluded telemetry/uninitialized bytes remain separate from performance evidence. The existing metadata/preallocation techniques are not rebranded as novel algorithms.

## Randomization, thresholds and publication limits

Aggregate seed 681492 and ASCII seed 20261004 reproduce all mode orders and adjacent variant orders exactly, with complete per-mode block identities. Resampling one whole within-mode pair per block is correct for these single-mode statistics. Modes within a block share host conditions; they must not be pooled as 60 independent observations or bootstrapped independently for a cross-mode combined decision.

List instead runs system then fixed, and append31, append1024, append8193, grow31 in fixed order. It resets seed 20261004 for each case, creating the same six AB/six BA pattern in all eight cases. Each **case** has twelve legitimate adjacent pairs, but the cases are not randomized cross-case blocks. A common pair index across List cases is not a contemporaneous host block. Cross-case temporal effects and profile comparisons have less protection than the Text mode blocks. The List results justify the stated case-specific observations, not an overall workload-weighted performance effect.

The aggregate preregistration is retained both as a separate input and in raw results. It requires known-large estimate >1.03 and lower 95% bound >1; rejection requires supported candidate/baseline slowdown >3% for no-query or >5% for short/unknown/Unicode. In the displayed baseline/candidate direction, negative rejection is `upper < 1/threshold`. The runner implements that direction correctly. Known passes decisively. No material negative-control rejection occurs. Unknown nevertheless has a retained ~1.078% point slowdown and no-query ~0.475%; Unicode is unresolved around parity. Non-rejection is not proof of no slowdown or universal equivalence.

ASCII's saved decision is >3% median control slowdown with an interval excluding parity, a different rule from aggregate's lower-bound test. Its no-query and Unicode point effects are below that limit. List has no separately archived pre-run statistical threshold document in the inspected set; its reported residual slowdown is a tradeoff description, not verified preregistered noninferiority. The repeated earlier candidate designs and exploratory selection also prevent treating final estimates as unbiased estimates of a randomly selected optimization.

The 95% intervals are pointwise. With five aggregate modes, several controls and multiple prior experiments, they do not give a 95% joint assurance that all claims hold. As a supplementary sensitivity I retained 99% pointwise bootstrap intervals using the same resamples (a Bonferroni-style five-comparison check, **not** a calibrated familywise guarantee). Known [2.459284, 2.504631] and short [1.079152, 1.093601] remain strong; no-query [0.987497, 1.000144] includes parity. The declared thresholds remain well outside the relevant sensitivity ranges. This supports the large benefit and acceptable measured tradeoff, while weakening any insistence on a statistically certain half-percent no-query loss.

Adjacent pairing/randomization mitigate drift, but independence, exchangeability, random population sampling and unmeasured host behavior are not established. Seeded pseudo-random order is not random workload sampling. Bootstrap precision describes these twelve ratios under its resampling model; it excludes new hosts, compilers, allocators, source layouts, fragment counts and application mixes. Cluster sensitivity covers one short dependence scale only. All three reported intervals must accompany their observed-session scope.

Aggregate load1 was about 10.04→9.34 with the paced ~8% soak active; ASCII load1 about 12.16→12.46. Other deliberate project jobs being paused is inherited coordination evidence, not a complete recorded host process census. List does not retain equivalent load metadata. CPU time excludes time descheduled but still responds to CPU frequency, cache/memory interference and system work. The absence of large wall stalls is not a quiet-host guarantee. Older native/application pairs under Granola/Backblaze load were not recomputed or accepted as quiet-speed evidence in this audit.

The aggregate archive explicitly reports the resource correction: outer CPU240s/output256MiB/taskpolicy768MiB/nice15; runner timeout30s; the separately stated child CPU60s rlimit was **not installed**. Source confirms the 30-second subprocess timeout; this lane did not independently observe installation of the outer limits. This is a genuine protocol deviation, with no failed/near-timeout child in the saved measurements and no threshold change. The source guards input bytes/repetitions and asserts final expected sizes; it does not implement a continuous 32 MiB live-payload counter in the timing binary. That logical bound is a workload/source premise, not measured peak managed bytes. `ru_maxrss` is a process resource observation, not allocation accounting.
