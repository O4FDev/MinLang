## The kept change

- `list_next_capacity(0)` returned 2, then doubled (2→4→8→16…), so a List that ends up with 3–8 elements
  reallocated three times. Starting at 4 makes that one reallocation and costs 16 bytes only for a List that
  actually grows: an empty `[]` still has `values == NULL, capacity == 0`, so nothing is allocated early.
- The same line in both runtime fragments (`minyar_collections.h` plain runtime, `minyar_cycle_collections.h`
  the cycle runtime every Minyar program builds today). The bounded-pool branch (capacity 3) is untouched:
  pools size blocks from the page, not from this hint.
- Not observable: `capacity` never reaches a program (`length`, order, iteration, printing, sorting and
  aliasing are unchanged); the only effect is that a growing List reallocates less.
- Two tests pinned the old policy, both about internal counts, not language behaviour:
  `tests/peer-rust-go-zig.min` required `storage_moves >= 4` for a 40-element List (the moving-reallocator
  path); four slots give three moves, so the guard is `>= 3` with a comment (`951a1429a`).
  `tests/memory-research-list-reserve.c` models the growth policy; its model now starts at four slots
  (`2a2de6398`). No other test changed.
